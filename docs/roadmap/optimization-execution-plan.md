# 当前优化执行计划

更新时间：`2026-05-21`

本文档只负责把当前优先级展开成可执行步骤。事实和边界统一看 `../guides/engineering-audit.md`；优先级顺序统一看 `current-priorities.md`。

## 适用范围

- 当前默认部署模型：单机、SQLite、`docker-compose`、单实例或少量 worker
- 当前优化目标：先把单机模型做稳、做清楚、做可运维，再决定是否继续走多节点或独立中间件
- 当前不做的事：为了“看起来更像分布式”而提前引入 Redis、队列系统或更复杂部署编排

## 推荐优化顺序

### Phase 1：固化管理会话与部署边界

目标：

把现在“代码里已经做对，但部署上还可能配错”的边界变成明确检查项。

工作项：

1. 在部署文档里明确 same-site cookie、反向代理、HTTPS 和跨域边界
2. 在 `.env.example`、`docker-compose.yml` 和运维清单里补齐管理员会话相关说明
3. 评估 CLI / scheduler 是否继续保留共享 header 密钥，还是迁移到单独凭证

验收：

- 新部署按文档即可跑通管理员登录和写操作
- 代理配置不满足前提时，运维可以快速定位问题
- 管理台与自动化任务的鉴权模型边界被文档明确写清

### Phase 2：补齐 `/repos` 共享缓存治理

目标：

把“能跨 worker 复用”的缓存，补成“可控、可观察、可清理”的缓存。

状态：已落地首轮治理。

工作项：

1. `cache_entries` 已增加过期清理入口：`POST /metrics/cache/cleanup?namespace=repos&limit=1000`
2. `GET /metrics/cache` 已暴露条目数、过期条目、近似 payload 字节数、本地命中、共享命中和 miss 计数
3. `/repos` 共享缓存已增加命名空间条目数和 payload 字节数上限，避免缓存值无限增长
4. 缓存巡检与清理步骤已写入 `../guides/runtime-consistency.md`

验收：

- `cache_entries` 不会无限增长
- 管理员能够看到共享缓存大致规模和命中情况
- worker 间仍能复用缓存值，且失效语义不倒退

### Phase 3：统一开发与测试运行时基线

目标：

降低“环境问题先于业务问题”的调试成本。

工作项：

1. 保持根目录脚本作为唯一推荐验证入口：`npm run api:test`、`npm run web:test`、`npm run web:lint`、`npm run web:build`
2. 把 Python `3.11` - `3.13`、Docker fallback、前端依赖安装要求写进开发入口和排障说明
3. 对脚本层继续补回归，避免运行时探测逻辑再次退化

验收：

- 新环境按文档可以完成一次完整验证
- 运行时不满足要求时，脚本会给出明确回退路径
- 修改脚本或运行流程时，文档和校验一起更新

### Phase 4：只有在数据证明需要时，再评估外部缓存或多节点

目标：

把架构升级建立在真实瓶颈上，而不是预先设计。

触发条件：

1. SQLite `cache_entries` 治理完成后，命中率仍不足以支撑 `/repos` 热点查询
2. 单机少量 worker 已经成为瓶颈，且瓶颈能明确归因到共享缓存或共享状态层
3. 运维上已经需要多节点部署，而不是“未来可能需要”

迁移前必须先回答：

1. 是缓存压力在先，还是任务调度压力在先
2. 是只需要把 `/repos` 缓存迁到外部，还是连运行态/任务系统一起升级
3. 新组件带来的运维复杂度是否值得当前业务规模承担

如果验证命令、Python 版本要求、Docker fallback 或前端依赖前置条件发生变化，统一更新 `../../CONTRIBUTING.md` 与 `../../scripts/README.md`，不要在本页重复维护同一份运行手册。
